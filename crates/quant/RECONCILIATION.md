验证日期：2026-09-30 至 2026-10-01。代码在 `feat/quant-jsg-v2` worktree；所有数据库操作为只读，没有修改 quent 源码或数据库表。

## 冻结与原实现对账

数据来自本机 ClickHouse 26.3.7.8 的 `stock_data`。2026-04-01 至 2026-06-30，共 60 个回测交易日，加 30 个预热交易日，450,354 行。全量 Arrow 位于本 worktree 的 `tmp/real-2026-q2`，原 Python SQL 响应、源文件哈希和逐日轨迹位于 `tmp/reconciliation`。这些体积较大的文件保留在本地，不加入 Git。

`reconcile-jsg.py` 直接导入 quent 的 `JSGStrategy`、`BacktestBroker`、`TradingEngine` 和 DB 查询逻辑。输入 bar 来自冻结的 Arrow，Python 原 DB 查询通过只读录制器保存为 Arrow 文件；再次运行不带 `--capture` 时，完全使用录制结果，缺失任何查询或源代码/输入哈希变化都会失败。原 broker 的每日快照和策略结束后的真实账户权益分别记录，避免旧快照记账时点混入比较。逐日观察宽度使用独立 DB 缓存，避免观察代码修改原策略的缓存。

这验证的是**冻结 bar 驱动的原策略与原 broker**，不包含原项目的数据流分块、外部风控管理器或服务运行器。CH 的多次查询不是跨表事务快照；查询结果在录制后不可变，但录制期间需要源库保持历史数据稳定。

| 项目                 | 存在差异的交易日 |
| -------------------- | ---------------: |
| 行业宽度全部分组     |               60 |
| 周调仓目标的有序列表 |                2 |
| 成交/拒单列表        |               13 |
| 期末股票数量         |               35 |
| 现金 / 权益          |          55 / 55 |

12 次周调仓的目标股票**集合全部相同**。2 次顺序差异不是浮点容差问题：原股本查询仅限制 `change_date`，会使用尚未公布的数据。例如 2026-04-17，`sz.002486` 原查询使用 2026-04-30 才公布的 824,283,100 股；Rust 准备数据使用当日已公开的 828,127,200 股。因此它与 `sz.002319` 的市值顺序不同。新适配器要求股本变更日与公布日均严格早于交易日。

首个成交分歧是 2026-04-09：原实现卖出 `sz.003003`，Rust 卖出 `sz.002188`。原策略的涨停打开判断把复权收盘价与原始 `preclose` 比较；Rust 统一使用原始价格判断涨跌停。原 broker 的即时收盘订单又使用开盘价和已经更新成当日收盘的 `last_prices` 检查涨跌停。Rust 按实际成交时点、原始昨收价校验。这些行为差异会累积到后续数量、现金与权益，不能声称两个成交模型完全等价。

宽度差异主要来自样本日期：原 `get_price(count=20)` 会带入停牌/缺失当天行情股票的最近 20 条记录；Rust 的当前日分组只包含当前日有效 bar，未知行业不参与分组。行业排序以代码作为明确的同分规则。原 pandas 按行业名称排序。Rust 还固定卖单先于买单、现金不足时按整手部分成交；原 broker 保留提交顺序、资金不足时整单拒绝。每日收盘即时订单的费用计入 Rust 当日权益，原每日快照在策略即时订单之前保存。

原始逐日差异摘要保存在 [real-q2-differences.json](fixtures/real-q2-differences.json)。缩小后的真实价格回归样本在 [fixtures/real-q2](fixtures/real-q2)：21 只曾被选中的股票、1,890 行，约 228 KiB，仍覆盖全部 90 个会话。Rust 测试比较每个回测日的宽度、目标、订单、持仓、现金和权益。这是精简的真实价格测试股票池，其收益不代表全市场回测。

## 数据缺口和 v2 成交模型

实际库中 `index_stocks` 的主键是 `(index,code)`，没有退出事件；`finicial_report` 的主键是 `(report_date,code)`，修订会覆盖旧记录。当前库也没有明确公司行为表和每日实际涨跌停价。这些历史信息不能从剩余记录可靠恢复，当前实测仍使用明确标记的 `jsg-adjusted-v1` 研究模型。

新增 `jsg-raw-v2`：复权收盘只用于 MA20；原始价用于成交、持仓股数与现金账。支持 record/ex/pay/可交易日期、明确现金分红及扣税、送转股、零碎股现金、应收分红、跨日价格限制、T+1、按成交量参与率限制数量、整手买入与整仓零股卖出。费用表按日期提供佣金覆盖值、最低佣金、过户费用与卖出税费，费用合计按分取整。未指定分期佣金时使用策略配置佣金。费用和价格限制均由数据/配置给出，不内置一个永久不变的法定费率。

分红在除权时计入应收权益，支付日才释放可用现金；送股在可交易日期前锁定。遇到除权事件，取消该证券隔夜旧目标订单。公司行为缺失、每日价格限制缺失、费用表未覆盖起始日期时，raw-v2 直接拒绝运行。`tPlusOne=false` 不会关闭 raw-v2 的 T+1。

这仍是**日线研究撮合**：成交量是全日上限估计，不能证明开盘/收盘瞬时存在对应流动性。支持普通 100 股买入单位与现金/送转分配，尚不模拟逐笔排队、配股缴款、复杂重组或持仓期相关的延后税补扣；扣税金额应由明确事件提供。行业仍沿用旧库的生效日期，没有独立公告时间。严格模式检查新增数据合同及覆盖记录，不等于对所有市场事件给出无偏保证。

[history-schema.sql](sql/history-schema.sql) 描述可选源表，不会由工具执行。`index_membership_history` 是加入/退出事件，`financial_revisions` 按公布日保留多个修订，`research_coverage` 记录经过外部审核的覆盖区间。只创建空表不会通过严格模式。原生集成测试在独立嵌入式 ClickHouse 中验证退出公告和财报修订不会提前可见，并验证缺失数据、文件篡改、目标目录已存在时的处理。

## 实际负载性能

大样本：2024-01-02 至 2026-07-31，654 个会话，其中 624 个回测日，3,275,552 行，269,269,992 字节（约 257 MiB）。单次回测实际产生 1,277 笔成交、10 笔拒单；比原先只有少数成交的合成吞吐测试更接近策略负载。

| 操作                                  |          实测 |
| ------------------------------------- | ------------: |
| ClickHouse 查询 + Rust 解码/写分片    |        1.44 s |
| 原生快照导出总耗时                    |        1.48 s |
| Rust 单参数 JSONL 回测，3 次中位数    |        0.69 s |
| 同上进程峰值 RSS                      | 19.0–19.1 MiB |
| 16 参数，共享解码和特征，1 线程中位数 |        2.01 s |
| 同上，8 线程中位数                    |        0.92 s |
| 8 线程进程峰值 RSS                    | 32.5–33.3 MiB |
| 浏览器新项目首次导入                  |        2.17 s |
| 浏览器 WASM 回放                      |        1.37 s |

共享特征前，同一 16 参数负载的串行中位数为 2.63 s、8 线程峰值 RSS 约 56.8 MiB。最终共用 MA20 窗口、行业宽度和候选排序；不同风控参数的组合通过与独立回测逐项比较指标验证。

原生耗时包含 SHA-256 文件校验和结果写出，操作系统页缓存未清空。浏览器测试使用新项目，但操作系统和自动化浏览器运行环境已预热；它不代表磁盘物理冷启动。CH 返回的摘要是服务端响应头观测：读取约 1,467 万行、778 MB，查询摘要 0.38 s、内存 477 MB；响应头中 `result_rows` 为 0，因此不能拿它代替实际客户端读出的行数。

浏览器主页面 JS heap + backing storage 采样峰值约 166 MiB，**不包含单独计算 worker 的全部 WASM 内存**。通过 CDP 识别自动化 Chromium 进程树后，50 ms 采样 RSS 为基线约 631 MiB、峰值约 751 MiB；这个自动化浏览器可能还有其他上下文，而且共享页按进程重复计数，不能把 751 MiB 当成此应用的独占内存。

结果每 5 个会话落成一个 JSON artifact；WASM 和浏览器均只保留有界结果块，累计指标在线计算。主界面保留最多 2,048 个净值预览点、最近 200 笔订单、最近一次调仓；查询指定日期区间才读取对应块。完整 JSON 导出逐块写临时 OPFS 文件，并保留全部日线、订单和调仓记录。缓存保存结果块的引用，避免恢复时重新装载完整订单。

参数并行只并行独立组合，单组合沿时间顺序处理。Arrow 每日只解码一次，滚动价格窗口、行业宽度和候选排序也只计算一次，避免 16 组参数重复处理相同数据。线程数显式限额，不引入第二套数据库或常驻后端服务。

同一大样本的原生 JSONL 与浏览器完整 JSON 导出逐项比较通过：624 个日线点、1,287 条订单、全部调仓、持仓、现金和统计指标一致，本次最大数值差为 0。最终验证通过 875 项 TypeScript、20 项 Rust、7 项 Python 边界/对账与 2 项原生 ClickHouse 集成测试，以及浏览器导入、缓存、恢复、取消、移动端流程和 Quant Lab / Studio 生产构建。

复现命令见 [README.md](README.md)。
