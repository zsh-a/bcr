# 个人知识库与 Git 同步

入口：Studio 导航中的「个人知识库」，或直接访问 `/knowledge`。

这是独立于 Reader 的本地优先 Markdown 知识库：可以直接手写笔记，也可以把已有资料集合的摘录、笔记和来源快照导入。无需部署 SiYuan / Trilium 服务，不同步它们的内部数据库。

## 开始使用

1. 运行 `bun run studio`，打开 `/knowledge`。
2. 新建笔记，填写标题、Markdown 正文、逗号分隔的标签，可按集合分类。输入时备份草稿，停顿 500ms 后保存到当前工作区元数据；界面显示保存状态。
3. 使用全局搜索的「个人笔记」分类检索正文；导入普通 Markdown，或从「资料集合」导入已有摘录。重复导入同一摘录不会覆盖已经整理过的笔记。
4. 「导出这篇笔记」生成带元数据的 Markdown；「导出知识库」生成包括集合、Markdown 和引用 JSON 的 ZIP。ZIP 可解压后放入同步仓库；本期界面不提供 ZIP 恢复入口。

未连接仓库也可以编辑、搜索和导出。数据属于当前浏览器配置文件与网站 origin；清理网站数据或使用隐私窗口可能丢失本机数据。建议定期导出或同步。

## 两台设备使用同一仓库

1. 在 GitHub 创建一个**私有仓库**，勾选添加 README，使 `main` 分支存在。
2. 创建 fine-grained personal access token，只授权该仓库的 **Contents: Read and write**。不需要工作流或组织管理权限。组织仓库可能还需要组织批准；受保护分支可能不允许直接推送。
3. 第一台设备打开「连接」，填写用户/组织、仓库、已有分支和 Token，点击「保存连接」再「立即同步」。
4. 第二台设备填写同一连接，点击「立即同步」，即可拉取笔记。编辑后再次同步。
5. 可选开启「本次会话自动同步」：笔记保存后约 3 秒、恢复联网、窗口聚焦时同步；知识库处于活动页面时每 30 秒检查一次。页面关闭或切到其他应用后不做后台同步。

Token 仅存页面内存，刷新后重新填写；不写入 localStorage、工作区元数据、导出文件或仓库。连接配置会保存。所有 GitHub 请求直接从浏览器发往 `api.github.com`，不经过额外代理。没有 Token 时本机笔记仍可使用。

私有仓库**不是端到端加密**：GitHub、仓库协作者及持有 Token 的人可能访问笔记。不要存入不适合上传 GitHub 的敏感资料。删除当前文件也不会擦除 Git 历史中的旧内容。

## 存储格式

```text
knowledge/
  manifest.json               # 格式声明：bcr-knowledge / version 1
  notes/<stable-id>.md         # YAML 元数据 + 原始 Markdown 正文
  citations/<stable-id>.json   # 引用快照、来源身份与本地回跳位置
  collections/<stable-id>.json
```

标题重命名不改变文件身份。可以在外部编辑器修改 Markdown 正文，但需保留 YAML 中的 `bcr`、`id`、标题、时间、标签和集合字段，且文件名必须与 ID 一致。导入一般 Markdown 不要求这些元数据；应用会分配新身份。

仓库中其他文件不受影响。不上传 SQLite 数据库、检索索引、模型、缓存、Token、本机修订记录，也不上传 Reader 原书、PDF、音视频或图片附件。引用文字在另一台设备可读；「回到原文」需要该设备已有对应源资料。

此格式为后续 AI 检索、引用溯源与可审核修改提供基础；当前已接入单篇笔记的 AI 改写／续写（见下节），向量数据库、MCP 与自动改写代理仍未接入。

## AI 编辑（可选）

笔记编辑器提供「改写 / 续写」：把光标所在段落或选中片段交给模型，先给出一份**待应用**的改动，确认后才写入笔记。没有配置接口时这部分完全不可见之外的功能，本地编辑与同步不受影响。

- **范围由编辑器决定，不由模型决定**。模型只被要求返回该范围的替换文本；它与原文的差异在本地计算成一个最小替换区间。因此改一段不会重写全文，未触及的部分保持逐字节不变，多设备合并与冲突检测仍然有效。
- **先预览后写入**。预览显示将要发生的最小改动；「应用到笔记者才会落盘。若模型运行期间你继续打字，这份改动因为基准已变而被丢弃（不会写坏正文），并给出提示。
- **改前留版本**。应用前的正文会自动进入「历史」（与手工编辑同一机制），可用 `Ctrl/⌘+Z` 或历史恢复。
- **接口**：任意 OpenAI 兼容端点（官方 API、Ollama、LM Studio、网关）。填写接口地址、模型名与密钥；**密钥只保存在本页内存**，与 GitHub Token 同规格，刷新后需重新填写，也不写入本地存储、导出或仓库。本地端点可留空密钥，此时不发送 `Authorization` 头。
- **加载时机**：运行时是约 3.5 MiB 的 wasm 模块，只在第一次点击「改写 / 续写」时才下载；不使用 AI 的读者不会付出这份体积。

实现分为三层：`edit.ts` 是与来源无关的区间编辑协议（预览、应用、失效判定都在此），`noteAgent.ts` 把指令变成一份改动提案，`agentRuntime.ts` 负责 wasm 边界。写入始终经由既有的 `KnowledgeStore.saveNote(note, base)`，不新增写入路径。

运行时来自独立的 `agent-runtime` 仓库，以 submodule 固定在 `crates/agent-runtime`，用 `bun run build:wasm:agent` 编译到 `crates/agent-wasm/pkg`（生成物不入库，与 `crates/kernels/pkg` 一致）。

## 同步与恢复规则

- GitHub Git Database API 按目录差异生成 tree / commit，仅以 `force: false` 更新分支；这是 Git 版本同步，不是本地 Git clone，也不是多人实时协作。
- 使用本机保存的共同版本进行三方合并。不同行的正文改动可自动合并；同一行、竞争插入、元数据同时修改、删除与修改竞争时保留冲突，不静默覆盖。
- 冲突记录持久化到本机，刷新仍在。打开连接面板对比共同/本机/远端版本，选择本机、远端或保留双方；解决后再同步。保留双方会给远端版本生成新身份。
- 网络请求期间继续编辑不会被同步结果覆盖；新修改可能留待下一次同步。
- 远端提交前先保存待确认回执。如果推送成功但响应丢失，或最终本地写入失败，下次同步核对提交祖先关系再恢复。
- 每次最多重试 3 次非快进更新。公共仓库、损坏数据、不完整 tree、受管文件中的符号链接、远端历史重写均停止同步，保留本地内容。
- 本机最多保留 100 个修改前版本，包含删除记录。「历史」可恢复为当前笔记；也可读取当前笔记最近 20 次 GitHub 文件历史。恢复后生成新提交，不回退或强推远端历史。

当前容量边界：最多 5,000 篇笔记、1,000 个集合，单篇正文 500,000 字符；单个同步文件 2 MiB，同步文件合计 16 MiB。本机状态连同历史、基线、冲突及回执限制 32 MiB。达到限制会报错而不是截断数据。大量长笔记与频繁修订应考虑后续分记录存储升级。

离线编辑不依赖 GitHub。生产版沿用现有 Service Worker：首次联网加载知识库，待 Service Worker 接管后再在线打开/刷新一次，缓存所需动态资源，之后支持离线重新打开。首次访问未缓存资源时仍需网络；开发服务器不提供离线冷启动。

## 验证

```bash
bun run test apps/studio/tests/knowledge.test.ts
# 先启动 Studio 开发服务器；模拟 GitHub，不使用真实 Token 或外网仓库
BASE_URL=http://127.0.0.1:5199 node scripts/verify-knowledge.mjs
# 生产资源与关闭页面后的离线冷启动
bunx vp -C apps/studio build
BCR_KNOWLEDGE_PRODUCTION=1 node scripts/verify-knowledge.mjs
# AI 编辑：用桩端点，不需要真实密钥或外网
bun run build:wasm:agent
BASE_URL=http://127.0.0.1:5199 node scripts/verify-knowledge-agent.mjs
```

单测覆盖格式验证、三方合并、持久化故障、双设备同步、提交响应丢失、推送竞态、历史恢复等；`knowledge-edit.test.ts` 另外覆盖区间编辑（最小区间、批量偏移、重叠与越界拒绝）、基准失效丢弃与「改前留版本」。浏览器走查使用两个隔离存储上下文，共享模拟 GitHub 对象数据库，覆盖全局搜索、双设备合并与冲突、刷新恢复、Markdown 安全预览、导入导出和移动端布局；AI 走查另行断言预览阶段不写入正文、改写只影响目标区间、应用前版本可恢复、未使用 AI 时不下载 wasm。开发版走查已加入 `scripts/verify-ci.mjs`。
