# Workspace Search 性能基准

## 运行

先在一个终端运行 `bun run studio`，另一个终端运行：

```bash
bun run bench:search
BCR_BENCH_SIZES=100,1000,5000 BASE_URL=http://localhost:5199 bun run bench:search
```

规模可配置为 1–50,000 条文档。脚本使用独立 Chromium 上下文及同源空页面，通过 Vite 加载当前 `packages/core/src/search.ts`，不启动 Studio 的业务界面，不访问外部服务。每种规模独立创建上下文，结果写入 `scripts/shots/search-benchmark.json`；报告包括浏览器版本、CPU、平台及物理内存信息。该生成目录被 Git 忽略。

## 语料与指标

固定生成器交替创建中英文 Reader 正文投影，包含重复短语、每 97 条出现一次的稀有证据以及唯一记录编号。每条投影保留真实引用字段；语料 hash 构造不计入索引建立时间。四个查询分别覆盖中文稀有词、英文稀有词、英文常见短语和无命中，固定结果上限 60。

每个查询先预热一次，再测量 5 次，查询之间让出事件循环。报告提供各查询及合并样本的 P50/P95、命中数量，以及查询阶段通过 `PerformanceObserver` 记录的主线程长任务数量和最长持续时间。P95 使用排序后的 nearest-rank，单个查询仅 5 次采样，因此其 P95 等于本轮最大值。

同时记录：

- 投影 JSON 字节数、索引建立时间和持久化 JSON 字节数。
- 序列化时间与从内存 JSON 重建索引的时间；它们不包含 SQLite/OPFS 磁盘 I/O。
- 查询及恢复前后的 JS 堆差值，包含语料、序列化字符串、临时对象及恢复后的第二份索引，不等同于单一索引的常驻内存。
- 恢复后的文档数量、稀有词命中和无命中断言，避免以错误或空索引产生“更快”的结果。

## 解读与后续优化

本基准测量开发模块中的核心搜索路径，不代表生产首屏、完整界面响应或低端设备表现。运行时尽量停止其它构建/测试，比较前后版本时使用相同机器、浏览器、语料和查询配置。当前仅记录结果，不设易受机器负载影响的 CI 硬阈值；语义检索、Worker 通信及真实磁盘成本应另设场景。

当前实现对常见短语会扫描大量正文、枚举命中，再统一排序截断。优先优化方向是预计算规范化字段、候选筛选与有界结果计算；随后评估移入 Worker 对主线程响应的改善。任何优化都需继续通过已有引用偏移、重叠片段和精确回跳回归。
